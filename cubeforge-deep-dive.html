Core System

The ECS — Entity Component System

This is the most important file in the whole project. Everything else depends on it. File: packages/core/src/ecs/world.ts

Plain-English Version: Imagine a giant spreadsheet. Each row is a "thing" in your game (a player, an enemy, a coin). Each column is a piece of data (position, velocity, color). Systems scan specific columns every frame to do their work — the physics system looks at "has velocity" rows, the render system looks at "has sprite" rows. That's ECS.

How entities are created

// An entity is just a number (ID)
type EntityId = number

// Creating an entity:
const playerId = world.createEntity()
// Returns e.g. 1, 2, 3... just a number

// Adding components to it:
world.addComponent(playerId, {
  type: 'Transform',
  x: 100, y: 300, rotation: 0
})
world.addComponent(playerId, {
  type: 'RigidBody',
  vx: 0, vy: 0, gravityScale: 1
})

// Destroying it later:
world.destroyEntity(playerId)
// That's it — all components removed automatically

How systems query entities

// Physics system asks: "give me all entities
// that have BOTH Transform AND RigidBody"
const bodies = world.query([
  'Transform',
  'RigidBody'
])

// Returns array of entity IDs — fast!
for (const id of bodies) {
  const rb = world.getComponent<RigidBodyComponent>(
    id, 'RigidBody'
  )
  rb.vy += GRAVITY * dt // apply gravity
}

// The query result is CACHED — repeated calls
// are O(1) until a component change invalidates it

The ECS uses an Archetype Pattern — a clever optimization that groups entities with identical component sets together in memory. This is how big game engines like Unity's DOTS work.

What an Archetype is

// These 3 entities share the same archetype:
// { Transform, RigidBody, Sprite }
//
// Entity 1: player    ← archetype A
// Entity 2: enemy     ← archetype A
// Entity 3: coin      ← archetype A
//
// This entity has a different archetype:
// { Transform, Sprite }  ← no RigidBody
// Entity 4: background   ← archetype B
//
// When physics queries [Transform, RigidBody]:
// → scans archetype A  ✓  (has both)
// → skips archetype B  ✗  (missing RigidBody)
//
// Result: no per-entity scan needed at all!

Archetype in world.ts

// Simplified from the actual code:
interface Archetype {
  key: string         // e.g. "RigidBody|Sprite|Transform"
  componentTypes: Set<string>
  entities: Set<EntityId>
  components: Map<string, Map<EntityId, Component>>
}

// When you add a component, the entity moves
// to the matching archetype (or a new one is created)
world.addComponent(id, { type: 'RigidBody' })
// → finds archetype { Transform, RigidBody }
// → moves entity there
// → old archetype loses this entity

Every world.query() result is cached. Calling the same query 100 times costs the same as calling it once — until a component changes.

// First call — scans archetypes, builds result list, caches it
const result1 = world.query(['Transform', 'RigidBody'])

// Second call — returns cached list instantly (no scan)
const result2 = world.query(['Transform', 'RigidBody'])

// Component mutated (e.g. player moved):
world.markDirty(playerId, 'Transform')
// → only caches that include 'Transform' are invalidated
// → other queries (e.g. ['Sprite','Text']) stay cached

// Next call rebuilds ONLY the invalidated cache entry
const result3 = world.query(['Transform', 'RigidBody']) // rebuilt

The ECS supports deterministic mode — given the same seed, the game will always play out identically. This is critical for replays, multiplayer, and debugging.

Seeded RNG (LCG algorithm)

// Linear Congruential Generator
// — a classic fast RNG used in games
world.setDeterministicSeed(42)

// Now Math.random() is replaced with
// a seeded version that produces the
// same sequence every time:
world.random() // → always 0.374... with seed 42
world.random() // → always 0.821... next call

// Use it in scripts for reproducibility:
const spawnX = world.random() * 700

World Snapshots

// Save entire world state to a plain object:
const snap = world.snapshot()
// → { entities: [...], components: {...}, tick: 1234 }

// Restore it (used by multiplayer rollback):
world.restore(snap)
// → world is exactly as it was at tick 1234

// ClientPrediction uses this to:
// 1. Save snapshot every frame
// 2. When server says "you were wrong at tick 50"
// 3. Restore snapshot from tick 50
// 4. Re-simulate forward to current tick
// 5. Player never sees a jump/glitch

The Game Loop

File: packages/core/src/loop/gameLoop.ts — The heartbeat of the engine. Runs 60 times per second.

The "spiral of death" problem: If the browser tab is hidden for 10 seconds, delta time would be 10 seconds, and everything would teleport. The GameLoop caps delta at 100ms to prevent this — a missed frame just plays a bit slow, not broken.

How the loop works

// requestAnimationFrame = browser's built-in
// "call me just before the next screen paint"
// Gives ~16.67ms between calls at 60fps

class GameLoop {
  start() {
    this.running = true
    this.lastTime = performance.now()
    requestAnimationFrame(this.frame)
  }

  private frame = (time: number) => {
    // Cap at 100ms — prevents spiral of death
    const dt = Math.min(
      (time - this.lastTime) / 1000,
      0.1
    )
    this.lastTime = time

    // Hit-pause: freeze sim for e.g. 0.1s on hit
    if (this.hitPauseTimer > 0) {
      this.hitPauseTimer -= dt
    } else {
      this.onTick(dt) // ← runs physics, scripts, render
    }

    requestAnimationFrame(this.frame) // ← schedules next frame
  }
}

Special features

⏸ Hit Pause

Call gameLoop.hitPause(0.08) to freeze the simulation for 80ms. Used for satisfying "game feel" moments — enemy death, big explosion. The screen freezes briefly then resumes.

🔒 Fixed Timestep

Pass fixedDt: 1/60 to always tick at exactly 1/60s. This makes physics fully reproducible regardless of real frame rate — essential for deterministic multiplayer.

⏯ Pause / Resume

Separate from start/stop — pause keeps state but stops ticking. Resume continues from where it left off. The game component wires this to window focus/blur automatically.

Order of operations every frame

1. Input.flush()
→
2. ScriptSystem.update(dt)
→
3. PhysicsSystem.update(dt)
→
4. TweenSystem.update(dt)
→
5. RenderSystem.draw()

The Physics System

File: packages/physics/src/physicsSystem.ts — Gravity, collision detection, and response. Runs at a fixed 60 Hz.

AABB collision — "Axis-Aligned Bounding Box." Every entity's hitbox is a rectangle that never rotates. This is simpler and faster than rotated shapes, and works perfectly for 2D games.

Every physics tick (1/60 second), the system does this for every entity that has a RigidBody and a BoxCollider:

Skip sleeping bodies

If a body hasn't moved in several frames and isn't being pushed, mark it "sleeping" and skip it entirely. Big performance win for levels with many static-ish objects.

Apply gravity

// gravityScale lets per-entity gravity tuning
// (e.g. a feather falls slower than a rock)
rb.vy += gravity * rb.gravityScale * dt

Integrate velocity → move the entity

transform.x += rb.vx * dt
transform.y += rb.vy * dt

CCD sweep (if enabled)

For fast-moving objects (bullets, fast enemies), a swept AABB test checks the entire path traveled this frame, not just the endpoint. Prevents "tunneling" through walls.

Broad-phase: find potential collisions

Uses archetype queries (not spatial hash by default) to get all collidable entities. Then checks AABB overlap in pairs. Only entities that overlap proceed to narrow phase.

Narrow-phase: resolve collision

// Calculate overlap depth on both axes
const overlapX = ...
const overlapY = ...

// Push entities apart on the SMALLER overlap axis
// (minimum translation vector)
if (overlapX < overlapY) {
  // Push horizontally
  transform.x += overlapX * side
  rb.vx = 0
} else {
  // Push vertically (landing on platform)
  transform.y = platform.y - entity.height
  rb.vy = 0
  rb.onGround = true
}

Apply friction and bounce

When on the ground, horizontal velocity is multiplied by 1 - friction each frame. Bounce coefficient determines how much velocity is preserved on impact (0 = stop, 1 = elastic).

Fire collision events

After resolving, emits 'collision' events on the EventBus so your game scripts can react (play a sound, decrease health, collect a coin).

The RigidBodyComponent is the data packet every physics-enabled entity carries. It's defined in packages/physics/src/components/rigidbody.ts.

interface RigidBodyComponent {
  // Velocity
  vx: number          // horizontal speed (pixels/sec)
  vy: number          // vertical speed (pixels/sec)

  // Physical properties
  mass: number        // affects impulse response
  gravityScale: number  // 0 = no gravity, 2 = double gravity
  bounce: number      // 0 = no bounce, 1 = perfect elastic
  friction: number    // ground friction multiplier

  // State flags
  isStatic: boolean   // true = never moves (platforms, walls)
  onGround: boolean   // set by physics, read in scripts for jumping
  isNearGround: boolean // within ~2px — enables "coyote time" jumps
  isKinematic: boolean // skips gravity — you control movement manually

  // Axis locking
  lockX: boolean       // can't move horizontally (fixed-column runner)
  lockY: boolean       // can't move vertically

  // One-way platforms
  dropThrough: number  // countdown: skip one-way blocking for N steps

  // Angular
  angularVelocity: number
  angularDamping: number

  // Performance
  sleeping: boolean    // physics skips sleeping bodies
}
🪜 One-Way Platforms

Tag a platform as one-way → collider only blocks from above. Jump up through it, land on top. Set rb.dropThrough = 3 to fall through it.

<BoxCollider oneWay={true} />
🏔 Slope Handling

Slope colliders let the player walk up angled surfaces. Physics applies slope friction and adjusts velocity direction to follow the surface normal.

🕳 Kinematic Bodies

Skip gravity and velocity integration. You move them with useKinematicBody() hook — ideal for elevators, moving platforms, doors.

🐇 Coyote Time

When rb.isNearGround is true (within 2px of ground), the player can still jump even if they've just walked off a ledge. Makes platformers feel less frustrating.

💫 Collision Layers

Each collider has a layer (bitmask) and mask. Only colliders whose layer matches another's mask interact. Bullets pass through walls but not enemies, for example.

🎯 CCD (Continuous Collision)

Fast objects (bullets, falling items) can pass through thin walls in a single frame. CCD sweeps a path between frames and catches these missed collisions.

The physics system fires events on the EventBus so your scripts can react without polling.

// In your game script, listen for collisions:
eventBus.on('collision', ({ a, b, normal }) => {
  // 'a' and 'b' are entity IDs
  const tagsA = world.getComponent<TagComponent>(a, 'Tag')
  const tagsB = world.getComponent<TagComponent>(b, 'Tag')

  if (tagsA?.tags.includes('player') && tagsB?.tags.includes('enemy')) {
    decreaseHealth()
    playHitSound()
  }
})

// When entities stop touching:
eventBus.on('collisionEnd', ({ a, b }) => {
  // e.g. player left a moving platform
})

The Rendering System

Two renderers: packages/renderer/src/renderSystem.ts (Canvas 2D) and packages/webgl-renderer/src/webglRenderSystem.ts (GPU).

🖌 Canvas 2D Renderer

Standard HTML5 canvas. Easy to debug, good for most games. Draws each sprite one at a time using the browser's 2D drawing API. Used automatically in simple setups.

Easy to understand Good for <500 sprites
⚡ WebGL2 Renderer

GPU-accelerated. Batches all sprites into a single draw call using instancing — sends data for all 8192 sprites to the GPU in one shot. Dramatically faster for large worlds.

8192 sprites per draw call GLSL shaders

Every frame, the renderer draws in this exact order (painter's algorithm — later draws go on top):

1. Clear canvas
Fill background color
2. Parallax layers
Background scrolls at fraction of camera speed — creates depth illusion
3. Apply camera transform
Shift canvas origin to follow player; apply zoom
4. Sprites
Sorted by zIndex + render layer; supports flip, tint, blend modes, tiling, frame sprites
5. Shapes
Circles, polygons, lines drawn with canvas paths
6. Text
Word-wrapped, shadow, stroke, custom font size/align
7. Particles
Per-particle: size-over-life, rotation, gravity, attractors
8. Trails
Fading polyline following entity movement
9. Debug overlays
Collider wireframes, FPS counter, nav grid (only in <Game debug>)
10. Post-process
Screen-space effects: blur, vignette, color grading

How camera follow works

// Camera doesn't "teleport" to player.
// It lerps (linear interpolates) toward it.

// Every frame:
camera.x += (target.x - camera.x) * smoothing
camera.y += (target.y - camera.y) * smoothing

// smoothing = 0.85 means "move 85% of the
// remaining distance each frame"
// Result: smooth, organic camera movement

// Dead zone: camera only starts following
// when player leaves a center rectangle
if (Math.abs(playerX - camera.x) > deadZoneW) {
  // start following
}

Camera shake

// Shake is applied as an offset on top of
// the smooth follow position.
// It uses quadratic ease-out to fade:

const progress = shakeTime / shakeDuration
const strength = shakeMagnitude * (1 - progress * progress)

camera.offsetX = (Math.random() * 2 - 1) * strength
camera.offsetY = (Math.random() * 2 - 1) * strength

// Result: violent shaking that smoothly
// decelerates to stillness

The animation system is a state machine — exactly like Unity's Animator. You define states (idle, run, jump) and conditions that trigger transitions.

// Before rendering, the Animator evaluates transitions:
for (const transition of currentState.transitions) {
  // Check all conditions for this transition
  if (transition.conditions.every(c => evaluateCondition(c))) {
    // Check exit time (don't interrupt too early)
    if (!transition.hasExitTime || animProgress >= transition.exitTime) {
      // Transition to new state
      currentState = transition.target
      animTime = 0

      // Fire enter/exit callbacks
      prevState.onExit?.()
      currentState.onEnter?.()
      break
    }
  }
}

// Then play the current animation clip:
const frame = Math.floor(animTime * fps) % totalFrames

The WebGL renderer uses instanced rendering — it uploads data for all sprites at once and the GPU draws them in parallel.

Vertex Shader (runs on GPU)

// This runs once per vertex, per instance
// "per instance" = per sprite in the batch
attribute vec2 a_position;   // quad corners
attribute vec2 a_texCoord;   // UV coordinates

// Per-instance data (one per sprite)
attribute vec4 a_transform;  // x, y, scaleX, scaleY
attribute float a_rotation;  // rotation angle
attribute vec4 a_tint;       // color tint

void main() {
  // Apply transform to position quad corners
  vec2 pos = rotate(a_position * a_transform.zw,
                    a_rotation) + a_transform.xy;
  gl_Position = u_matrix * vec4(pos, 0, 1);
}

How batching works

// 1. Every frame, build a Float32Array with
//    all sprite data packed together:
buffer[i*STRIDE + 0] = sprite.x
buffer[i*STRIDE + 1] = sprite.y
buffer[i*STRIDE + 2] = sprite.scaleX
// ... etc for all 8192 sprites

// 2. Upload entire buffer to GPU once:
gl.bufferData(ARRAY_BUFFER, buffer, DYNAMIC_DRAW)

// 3. Draw ALL sprites in ONE GPU call:
gl.drawArraysInstanced(TRIANGLE_STRIP, 0, 4, count)
// GPU draws 4 vertices × count instances
// in parallel — extremely fast!

The Input System

Files: packages/input/src/inputManager.ts, keyboard.ts, mouse.ts, touch.ts

Transient state — the key insight

// "Transient" means: only true for ONE frame

// Frame 1: player presses Space
keyboard.justPressed.add('Space')
keyboard.held.add('Space')

// After frame 1: flush() is called
keyboard.justPressed.clear()  // ← cleared!
// held still contains 'Space'

// Frame 2: Space still held
input.isPressed('Space')  → false  (only first frame)
input.isDown('Space')    → true   (still held)

// Frame 3: player releases Space
keyboard.justReleased.add('Space')
keyboard.held.delete('Space')

input.isReleased('Space') → true  (only this frame)

Advanced features

🎮 Input Contexts

Switch between control schemes (e.g. "menu" vs "gameplay"). In menu context, WASD navigates; in gameplay context, WASD moves the player. Prevents input bleeds.

🎯 Combo Detection

Define sequences like ['↓', '→', 'A'] and get notified when the player executes them within a time window. For fighting game moves.

📼 Recording & Playback

Record a session of inputs to a buffer, then play them back deterministically. Used for demos, automated testing, and replays.

👥 Per-Player Input

In multiplayer games, each player gets their own PlayerInput instance mapped to a specific gamepad or keyboard region.

How to use it in a script

// Your script receives (entityId, world, input, dt)
// 'input' is the InputManager
function movePlayer(id: EntityId, world: ECSWorld, input: InputManager, dt: number) {
  const rb = world.getComponent<RigidBodyComponent>(id, 'RigidBody')!

  // Movement: isDown = true while key is held
  if (input.isDown('ArrowLeft'))  rb.vx = -200
  if (input.isDown('ArrowRight')) rb.vx =  200

  // Jump: isPressed = true ONLY on first frame of press
  // Prevents holding Space from repeatedly jumping
  if (input.isPressed('Space') && rb.onGround) {
    rb.vy = -500
  }

  // Axis helper: -1, 0, or +1
  const axis = input.getAxis('ArrowRight', 'ArrowLeft')
  rb.vx = axis * 200
}

The Audio System

File: packages/audio/src/useSound.ts — A React hook wrapping the Web Audio API with pooling, groups, and fades.

Gain node hierarchy

// Web Audio API uses a node graph:
//
//   AudioContext (hardware output)
//        ↑
//   Master GainNode  ← global volume
//        ↑
//   Group GainNode   ← 'sfx' or 'music' volume
//        ↑
//   Instance GainNode ← per-sound volume
//        ↑
//   AudioBufferSourceNode ← the actual audio
//
// Fade in/out just ramps the gain value smoothly:
gainNode.gain.linearRampToValueAtTime(
  1.0,                             // target value
  audioCtx.currentTime + duration  // time to reach it
)

Instance pooling

// AudioBufferSourceNode can only play ONCE.
// To play the same sound many times rapidly
// (e.g. gunshots), you need multiple instances.
//
// The pool pre-creates N AudioBufferSourceNodes
// and recycles them:
//
// pool: [node1, node2, node3, node4]
//          ↑ free  ↑ free  ↑ playing  ↑ free
//
// play() → grab next free node → start it
// When it ends → return to free pool
//
// maxInstances (default 4) prevents 200
// simultaneous gunshot sounds

sound.play()            // grabs node from pool
sound.fadeOut(0.5)     // ramp gain to 0 over 0.5s
sound.crossfadeTo(newSrc, 1.0) // music transition
Multiplayer

The Networking System

Files: packages/net/src/room.ts, clientPrediction.ts, syncEntity.ts

The lag problem: In a multiplayer game, your input takes ~50ms to reach the server and come back. If you wait for the server's response before moving the player, everything feels laggy. The solution is "client-side prediction" — move immediately and correct if the server disagrees.

The Room class is a thin wrapper over a WebSocket transport. It handles JSON serialization and peer identification.

// Room wraps any transport (WebSocket, mock, etc.)
// All messages are JSON on the wire:
interface NetMessage {
  type: string      // e.g. 'player:input', 'entity:state'
  payload: unknown  // any data
  peerId?: string   // who sent it (set by server relay)
  tick?: number     // simulation tick (for ordering)
}

// Create a room:
const room = new Room({
  transport: new WsTransport('wss://yourserver.com/game'),
  onPeerMessage: (peerId, msg) => {
    // Another player sent something
  }
})

await room.connect()
room.send({ type: 'player:input', payload: { vx: 200 } })
room.onMessage(msg => console.log('received:', msg))

How rollback works

Save snapshot every frame

ClientPrediction keeps a circular buffer of the last 60 world snapshots — one per frame.

Player acts immediately

When you press right, the player moves right NOW without waiting for the server. The game feels instant.

Server correction arrives

"At tick 50 your position was wrong." The server's simulation takes precedence.

Rollback + resimulate

Restore snapshot from tick 50, re-apply all inputs since then. Player is now in the correct position. If the correction is small, the player barely notices a snap.

Code

class ClientPrediction {
  // Circular buffer of 60 snapshots
  private buffer = new Map<number, WorldSnapshot>()

  saveFrame(tick: number) {
    this.buffer.set(tick, world.snapshot())
    // Evict frames older than bufferSize
    if (this.buffer.size > 60) {
      const oldest = Math.min(...this.buffer.keys())
      this.buffer.delete(oldest)
    }
  }

  applyCorrection(serverSnap, tick) {
    world.restore(serverSnap) // ← rollback
    // Caller then re-runs simulation forward
    // from tick to current tick
  }
}

The Bridge

How React Talks to the Game Engine

The most creative part of the project. File: integrations/cubeforge/src/

The core idea: React is normally used to build UIs. Your friend figured out how to make it drive a game engine. When React mounts a <Sprite /> component, it adds a Sprite to the ECS. When React unmounts it (e.g. coin collected), the ECS entity is destroyed. React's tree IS the game world.

React Context = engine access

// EngineContext is created once by <Game>
// and provided to all children via React's
// Context API:

interface EngineState {
  world: ECSWorld
  loop: GameLoop
  input: InputManager
  events: EventBus
  assets: AssetManager
  renderer: RenderSystem
}

// Any component can access the engine:
const { world, input } = useContext(EngineContext)

// EntityContext holds the current entity ID:
const entityId = useContext(EntityContext)

How <Entity> works

// When React renders <Entity id="player">:
function Entity({ id, children }) {
  const { world } = useContext(EngineContext)

  const entityId = useMemo(() => {
    return world.createEntity()  // ← entity created!
  }, [])

  useEffect(() => {
    return () => world.destroyEntity(entityId) // ← cleanup!
  }, [])

  // Provide entityId to children via context
  return (
    <EntityContext.Provider value={entityId}>
      {children}   // <Sprite>, <RigidBody>, etc.
    </EntityContext.Provider>
  )
}

How <Sprite> works

// <Sprite> adds/removes SpriteComponent
// from the ECS entity when mounted/unmounted
function Sprite({ width, height, color }) {
  const { world } = useContext(EngineContext)
  const entityId = useContext(EntityContext)

  useEffect(() => {
    world.addComponent(entityId, {
      type: 'Sprite', width, height, color
    })
    return () => world.removeComponent(entityId, 'Sprite')
  }, [])

  // Sync prop changes to the ECS
  useEffect(() => {
    const c = world.getComponent(entityId, 'Sprite')
    if (c) { c.width = width; c.height = height; c.color = color }
  }, [width, height, color])

  return null // renders nothing to DOM!
}

What <Game> bootstraps

// Game.tsx is the "main function" of the engine.
// It creates and wires together:
const world    = new ECSWorld()
const loop     = new GameLoop(tick)
const input    = new InputManager()
const events   = new EventBus()
const physics  = new PhysicsSystem(world, events, gravity)
const renderer = new WebGLRenderSystem(canvas, world)
const scripts  = new ScriptSystem(world, input)

function tick(dt) {
  input.flush()          // 1. clear transient state
  scripts.update(dt)    // 2. run user scripts
  physics.update(dt)    // 3. simulate physics
  renderer.draw()       // 4. draw everything
}

loop.start()
input.attach(canvas)

Additional engine features

🕰 Time-Travel DevTools

<Game devtools> adds a frame scrubber and entity inspector. Records world snapshots and lets you rewind — like browser DevTools but for your game.

♿ Accessibility

The accessibility module generates ARIA descriptions of game entities for screen readers and logs state changes — rare in game engines.

🔌 Plugins

Pass plugins={[myPlugin]} to Game. Each plugin receives the engine state and can register new systems, components, or hooks. The HMR plugin enables hot-reload without losing game state.

🗺 Pathfinding

packages/core/src/nav/pathfind.ts — A* pathfinding on a nav grid. Enemies can navigate around obstacles without you writing the algorithm.

🎬 Tweens

tween(0, 100, 1.0, Ease.easeOutBounce, v => entity.x = v) — 20+ easing functions, chainable via TweenTimeline. For smooth non-physics animations.

🗂 Tilemap Merging

tilemapMerge.ts — Collapses adjacent same-type tiles into single large colliders. Reduces physics entities from 200 to 10 for a tiled level.

Where to Start Contributing

Now that you understand the codebase, here's a practical guide to getting started — from easiest to most complex.

🟢 Easy — Good First Issues

• Add a new easing function to tween.ts

• Add a new Sprite blend mode to the WebGL renderer

• Write missing tests in packages/*/src/__tests__

• Add a new keyboard shortcut in the DevTools

• Improve TypeScript types in a component interface

🟡 Medium

• Add a new collider type (e.g. PolygonCollider)

• Extend the Animator with blend trees

• Add a useKinematicBody hook improvement

• Add spatial audio to useSpatialSound.ts

• Build a new example game

🔴 Hard

• Improve physics broadphase (integrate SpatialHash)

• Add WebRTC transport to @cubeforge/net

• Implement a constraint/joint solver

• Add 3D support (new renderer package)

📐 Design Principles to Follow

• Data-only components — no logic in components, only data

• Systems read/write ECS — logic lives in systems

• React hook = ECS bridge — mount → add, unmount → remove

• Zero runtime deps — the engine imports nothing outside itself

• TypeScript strict — no any, full inference
